# bhc-driver

Compilation orchestration for the Basel Haskell Compiler.

## Overview

This crate runs the compilation pipeline for the `bhc` CLI, `bhci` and other embedders: it preprocesses and parses source files, discovers imported modules, lowers and type checks them, optimizes Core, dispatches to the native, WASM or GPU backend, writes `.bhi` interfaces and links executables. It also runs programs directly through the Core interpreter.

## Modules

| Module | Responsibility |
|--------|----------------|
| `lib.rs` | `Compiler`, `CompilerBuilder`, the pipeline, module discovery and ordering, `.bhi`/`.bhc` handling |
| `cpp` | Built-in "traditional" CPP preprocessor (`#if`, `#ifdef`, `#define`, `#elif`, ...) for files with `{-# LANGUAGE CPP #-}` |
| `report` | `ComprehensiveKernelReport` for `--kernel-report` in the Numeric profile |

## Pipeline Stages

Per module, `CompilePhase` names the stages reported to `CompileCallbacks`:

```
Source file
     │  (CPP if enabled)
     ▼
Parse                bhc-parser
     │
     ▼
Lower AST → HIR      bhc-lower (name resolution, imports via .bhi)
     │
     ▼
TypeCheck            bhc-typeck
     │
     ▼
CoreLower            bhc-hir-to-core
     │
     ▼
CoreOptimize         monomorphize → simplify → demand + worker/wrapper
     │               → dictionary specialization → (Numeric) list fusion
     │               escape analysis (Embedded profile)
     ▼
TensorLower/LoopLower   Numeric profile or --tensor-fusion: kernel analysis and reports
     │
     ▼
Codegen              native: bhc-codegen (LLVM) → .o
     │               wasm targets: bhc-wasm → .wasm
     │               GPU target / PTX emit: bhc-gpu → .ptx
     ▼
Link                 bhc-linker (native only)
     │
     ▼
Executable
```

On the native path the Loop IR produced for numeric kernels is used for reports and the WASM/GPU backends; native code is generated from Core.

## Driver API

```rust
use bhc_driver::{Compiler, CompilerBuilder};

let compiler = CompilerBuilder::new()
    .profile(Profile::Default)
    .opt_level(OptLevel::Default)
    .output_path("main")
    .import_path("src")
    .build()?;                       // or Compiler::new(options)

// Whole program: discover imports from the entry file, compile in dependency order, link
let outputs = compiler.compile_with_discovery("Main.hs")?;

// Single file
let out: CompileOutput = compiler.compile_file("Main.hs")?;

// Separate compilation (`bhc -c`): write .o to odir and .bhi to hidir, no link
let out = compiler.compile_module_only("src/Foo.hs")?;

// Type check only
compiler.check_file("Main.hs")?;

// Interpret through the Core evaluator
let (value, display) = compiler.run_file("Main.hs")?;
```

Other entry points: `compile_source`, `compile_files` (independent files), `compile_files_ordered`, `check_files_ordered`, `check_with_discovery`, `check_with_discovery_with_deps` (extra dependency source roots), `run_source`, `run_module`. `CompilerBuilder` also sets `target`, `odir`, `hidir`, `package_db`, `package_id`, `define` (CPP macros), `hackage_package`, `emit_kernel_report`, `tensor_fusion` and `compile_only`.

## Separate Compilation

With `-c`, each module produces an object file and a `.bhi` interface (generated by `bhc_interface::generate::generate_interface`). Alongside the `.bhi` the driver writes a `.bhc` sidecar containing the module's serialized Core bodies and newtype/synonym definitions, which the monomorphization pass loads to specialize imported polymorphic code. `--package-db` directories are searched for interfaces of already-compiled packages.

## Parallel Compilation

`compile_files` compiles a set of independent files in parallel with `rayon`. Dependency-ordered builds (`compile_files_ordered`, `compile_with_discovery`) compute a topological order of the import graph, report circular imports as errors, and compile modules in that order so each module sees its dependencies' interfaces.
